## 1. Purpose, users and success

S2C is a universal Markdown-guided development skill with optional local Python guards. It supports both development of S2C itself and application of its workflow to an authorized host repository. The product converts a stated need into a reviewable requirement, design, task, scoped implementation, test evidence and resumable handoff. ChatGPT/Codex provides the interactive agent; the repository supplies durable records. An API, database, MCP server, vector engine or autonomous worker fleet is not required for the MVP.

Actors: requester/product owner defines business goals and scope; developer/agent prepares artifacts and changes within authorization; technical reviewer evaluates design and code; security/host owner accepts applicable boundary and operational risks; release owner authorizes delivery. These are responsibilities, not invented named assignees. One person may hold several roles, but self-authorship is not independent approval.

Proposed acceptance targets: 100% of active BR requirements have measurable AC and forward/reverse trace or a visible blocking gap; every claimed verification has exact revision/environment/result; no mandatory security gate is waived by score; all required host/platform scenarios pass before stable release. Token/latency improvement has no numeric promise until benchmark data exists.

## 5. Lifecycle: A → A.1 → B → B.1

A is planning: P1 intent/scope; P2 specification plan; P3 source/research; P4 requirements/RTM; P5 feature design; P6 architecture/workflow; P7 Risk Discovery; P8 Risk Management; P9 design handoff. A.1 validates the entire package before authorized implementation.

The seven-stage business view below is an end-to-end process view, NOT seven coded Workflow Guard phases. Risk discovery/management repeat whenever evidence changes.

| Business stage | A/B responsibility | Current runtime correspondence | Exit evidence |
| --- | --- | --- | --- |
| DISCOVER | A/P1–P3; B startup refresh | DISCOVER | repository/source/scope snapshot |
| RISK_DISCOVER | A/P7, repeated throughout B | Manual control; no native phase | evidenced initial/changed risk register |
| SPECIFY_PLAN | A/P2–P6 | SPECIFY_PLAN | BR/AC, design, task, test and trace package |
| RISK_MANAGEMENT | A/P8–P9 before A.1; repeated in B | Manual control; no native phase | prioritized treatment and expected residual |
| IMPLEMENT | B, after A.1 and authorization | IMPLEMENT | scoped diff with requirement/task attribution |
| VERIFY | B internal verification, then B.1 | VERIFY | exact-source tests plus independent applicable acceptance |
| HANDOFF_REVIEW | A handoff and B delivery | HANDOFF_REVIEW for runtime B only | decisions, remaining work, risks and next safe action |

A.1 follows the full A package including risk treatment; it is not placed before Risk Management. B.1 follows actual implementation and internal verification. PASS does not independently authorize coding, merge or release. A.1 failure returns to affected P stages. B.1 implementation failure returns to B; changed requirements return to A/A.1. Source/policy drift invalidates affected evidence, not unrelated accepted history.

Normal flow: read baseline/RTM → select scoped task → resolve policy and context → risk review → prepare design → A.1/authorization → implement → verify → B.1 → handoff and delivery decision. Read-only review does not need a fake runtime session.

STOP applies at every point: freeze new mutations; record uncertain in-flight actions; capture task/session/ref/changed paths/approvals/evidence/risks/next action; preserve active session; persist only to allowed path and verify it, otherwise NOT_PERSISTED. Resume requires explicit continuation and fresh scope/policy/source review. Do not equate journal INVALIDATED with native PAUSED.

## 7. Risk, research and quality

Use the existing matrix: L/I 1–5, E=L×I; P0 16–25, P1 10–15, P2 5–9, P3 1–4. Scores are prioritization estimates. Path escape, unauthorized access, secret exposure and mandatory approval failures block regardless of score. Risk acceptance cannot authorize violating these invariants.

Taxonomy covers security, scope, privacy, data, requirements, architecture, dependencies/compatibility, implementation, performance, testing, workflow and migration. Group edges: duplicate, verified shared cause, causal chain, shared control, affected component. Component proximity alone does not prove shared cause. Preserve member severity; group priority is at least highest member/blocker; avoid adding correlated scores. A joint treatment closes no member until its own evidence and interaction checks pass.

Each run records BEFORE → chosen highest relevant risk → action → test/review evidence → AFTER. During A, AFTER means design disposition and expected residual; verified residual remains UNKNOWN unless evidence proves reduction. Existing RM-001..024 stay open as applicable. Workflow defects observed in code are repair backlog, not fixed by this document.

Research workflow: question → primary/peer-reviewed source search → verified source identifier/version → applicability/limitations → candidate control → comparison/experiment → decision and RTM/risk link. Do not invent DOI, benchmark or causal certainty. AST/vector retrieval is experimental; compare against current lexical baseline on fixed representative tasks using context relevance, missed mandatory policies, latency and context size. Report distribution and failed cases before selecting a technique.

## 12. Weighted Multi-Agent Review requirements and design

**Feature family**: BR-017..021 / proposed S2C-REQ-038..042 / F38..F42 / DES-088-01..05. The Google BRD's sections 21–22 is the business-facing explanation; this section is the repo-side canonical implementation contract. Both are DRAFT until revised by the authorized owner. No worker instance, runtime review API or test result is currently claimed.

**R0–R7 protocol:** REQUEST -> SCOPE+SNAPSHOT -> CLASSIFY(domain/artifact/risk) -> ALLOCATE(n, expert coverage, persona, budget, permission) -> INDEPENDENT REVIEW -> SYNTHESIS -> INDEPENDENT VALIDATION / HUMAN DECISION -> TRACE+HANDOFF. Every step supports STOP without fabricated `PAUSED` runtime status. Source/policy/role-catalog change invalidates affected outputs. No review result promotes policy status to approval.

**Role coverage** is tailored to observed domain and requested artifact: software (frontend/backend/full-stack, architecture, QA/tester, security, DevOps); data (DA/DE/DS, SQL/DB, quality/privacy); business/UX/compliance (BA/product/domain, accessibility, policy). Mixed artifacts may require more than one domain. A security-sensitive change requires a security lens; testability requires QA; data pipelines require data quality; missing mandatory coverage is an explicit GAP/BLOCK, not synthetic expertise.

**Persona** shapes adversarial/constructive/skeptical/pragmatic/compliance/exploratory checklists, not the reviewer’s credibility or authorization. Assign each worker a primary expert role, primary persona, and distinct scope or lens. Select exactly requested `n` when feasible; for `n=1` mark `LOW_INDEPENDENCE`; do not claim n-way independence if reusing one model/context or if workers read each other's drafts. Parallel execution only when the actual host supports and authorizes it; otherwise sequential context-isolated review where feasible, labeled `SEQUENTIAL`.

**Illustrative assignment heuristic** (to validate, not an empirically proved optimum):

```text
S(worker, slot) =
  0.35 * domainExpertiseFit +
  0.25 * artifactTaskFit +
  0.15 * perspectiveFit +
  0.15 * marginalCoverageGain +
  0.10 * budgetFeasibility
```

Components normalized to [0,1]. Weights belong to a versioned config and total 1; choose n via constrained assignment **with mandatory expert coverage, capacity, cost and permissions before optimizing S**. Review priority and severity use the existing risk matrix L*I (not S). Weighted reviewer support can be reported as contextual metadata but cannot vote away an independently evidenced P0/blocker, dissent, approval requirement or unknown fact.

**Worker finding schema (logical Markdown first):** `reviewId`, `workerId`, role, persona, `sourceRef` (path/tab/section/lines and revision), claim, observed evidence/reproduction, confidence+reason, risk category/L/I, scope and limitation, proposed correction, BR/REQ/DES/TASK/TC/evidence link, status. Synthesis preserves all raw findings, deduplicates by *verified* evidence/root cause, records agreement/conflict/dissent, issue score, unmatched evidence and unresolved blocker. Report is a recommendation: `PASS_WITH_NOTES` / `REVISE` / `BLOCK` / `INCONCLUSIVE`; **not** A.1/B.1 or owner `APPROVED`.

**Proposed artifact location and config:** development governance plan stays in existing files (no new parallel BRD). Per-run host review records may use a policy-approved `.agents/.reviews/<review-id>/` namespace only after owner/collision review; manifest, worker reports, synthesis, issues and decision stay linked to the existing session/handoff ledger. Review configuration may be added under `.source/.config/review.json` with schema/version, worker count/ceiling, role/persona catalog, normalized weights, coverage, budget, timeout, retry and quorum; **file/path names are proposed**, not current source or authorized host IO locations. Do not hardcode domain catalog or personalities into Python. Connector-hosted Google Docs follows provider permissions, not an imaginary local Path Guard sandbox. Sensitive content and untrusted instructions remain bounded.

### 18.2 Logical review state transitions (not Workflow Guard phases)
