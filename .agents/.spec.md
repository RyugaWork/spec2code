# Spec2Code v0.7.0 — Specification and acceptance contract

## Goal
Build a project-independent, repository-scoped Spec-to-Code agent skill with optional read-only GitHub Spec Kit bridging. v0.7.0 establishes a maintainable *development repository* layout, not an automatic rewrite of a host project.

## Authoritative layout
- Root: `AGENTS.md`, `README.md`, `pyproject.toml`, `.github/`, `.gitignore`.
- `.agents/`: versioned governance, features, plans, risks, checklists and internal handoffs; `.workflow/` stores reviewed lifecycle documentation.
- `.source/`: installable `SKILL.md`, `scripts/`, `tests/`, `references/`, `integrations/`, `.config/`.
- `docs/`: developer-facing documentation.

## Functional and security acceptance
1. Existing 0.6.x runtime behavior and APIs must remain unchanged by *layout-only* migration. An installed skill remains self-contained: `SKILL.md`, `scripts/`, `references/`, `.config/`.
2. Run tests with `python -m unittest discover -s .source/tests -v` on Python 3.10+, with Windows 3.14 tracked as a separate required platform.
3. No implicit Git merge, forced push, source deletion, remote fetch, Spec Kit file rewriting, or arbitrary shell access.
4. Any write is scoped to a validated Git worktree; managed-file collision preflight and adversarial Windows checks remain **OPEN** until verified.
5. Every functional change requires a plan, risks, tests/checklist, and a session-specific handoff.
6. Release status is **candidate**, not PASS, until required CI and independent safety checks succeed.

## Non-goals
No MCP transport/server, unattended editing agent, installer migration of existing sessions, or guarantee that a path guard sandboxes an unrelated agent process.

## Migration rules
Preserve historical records in `.agents/.handoffs/legacy-v0.6.4-*.md`. The earlier PLAN-070 changed only the development repository; PLAN-071 intentionally moves host runtime handoff output to `.agents/.handoffs/` and generated architecture output to `s2c/`. Never auto-migrate old data; `.agents/state/` remains unchanged and upstream Spec Kit retains ownership of `.specify/` and `specs/`.

## PLAN-081 — Agent governance acceptance contract (v0.8 candidate)

S2C is **agent-assisted, Markdown-directed**; the installed `SKILL.md` and host-approved instructions govern agent behavior, while Python utilities supply bounded local checks. A document instruction is not an OS-enforced access control. Do not advertise independent running agents, an MCP service, continuous background monitoring, or automated CI/CD execution.

Acceptance criteria for the Agents layer:
1. Root `AGENTS.md` provides a clear development entrypoint and routes to only existing governance/specification files; installed-host guidance is optional and cannot replace host-owned AGENTS.
2. Each logical role states inputs, evidence output and approval limits; roles can be performed sequentially by one interactive agent without implying delegation.
3. An agent distinguishes READ, PLAN, IMPLEMENT, VERIFY, DELIVERY permissions; scope and affected paths are factual and any new Git/host write requires appropriate authorization.
4. Active Spec Kit feature references originate from its documented feature pointer/override, never a Git branch. Upstream stages and optional quality gates are native agent actions; S2C's bridge only validates its implemented subset and does not write upstream artifacts.
5. Required host business/security/API documents are authoritative within their domains, while AGENTS, policy map, context pack, source snapshot, test output and handoffs have explicitly limited evidential meaning.
6. Documentation must never misrepresent PR #7 Workflow Guard defects, Windows TOCTOU or legacy migration as fixed. A READY machine gate is not a human approval.
7. Changes are verified by exact path/link/CLI comparison and real tests when available, with honest NOT RUN/SKIPPED labels; no change to runtime Python or test behavior is implied by PLAN-081.

## PLAN-082/083 — Requirements trace and interruptible workflow specification

The normative [system RTM](.traceMatrix.md) assigns stable `S2C-REQ-001..037` and `S2C-NFR-001..007` IDs, maps **every F01–F37** to a specific acceptance criterion, observed implementation/spec path, test method or explicit `NOT_MAPPED`, status and remaining gap. Matrix completeness means links exist; it is **not** equivalent to verification or requirement approval.

Agent-level STOP behavior is specified in [workflowSpecification.md](.workflow/workflowSpecification.md), with [stopAndHandoff.md](.workflow/stopAndHandoff.md) and a [handoff template](../.source/references/stop-handoff-template.md). Any normal phase can be interrupted. The agent must freeze new mutations, capture bounded actual state and test evidence, produce a human-readable handoff with verified persistence status or `NOT_PERSISTED`, and resume only after fresh policy/checkout/session/source and approval checks. STOP must not silently call `close`, `finish` or `merge`.

**Important acceptance distinction:** current Workflow Guard has five fixed phases and no machine STOP/RESUME/PAUSED state. F37 is **SPECIFIED at agent-document level, runtime PLANNED**. End-to-end stop/resume tests are not present. The unresolved PR #7 P0/P1 defects and Windows security/migration risks remain open independently.
