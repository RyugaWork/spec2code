## RTM conventions and evidence precision

- **Forward trace:** `Requirement ID → AC ID → Feature ID → Plan/Design → Exact source/document path → Actual test method OR NOT_MAPPED → Trace status → Gap`. **Reverse trace:** every F01–F37 has exactly one primary requirement row; NFR rows may reference multiple features. Test names are symbols, **not PASS proof**.
- `SOURCE+TEST`: code and mapped relevant test exist; no blanket AC acceptance. `PARTIAL`: known incomplete coverage or risk. `BLOCKED`: reviewed correctness defect blocks release. `DOC_REVIEW`: documentation exists, approval missing. `SPECIFIED`: desired agent-level behavior documented but no runtime feature test. `PLANNED`, `DEFERRED`, `OPEN`: remaining work. `EXCLUDED`: deliberate non-goal, not a delivered product capability.
- **Execution evidence is separate:** exact-head earlier [push CI #43337690688](https://github.com/RyugaWork/spec2code/actions/runs/43337690688) on `d49da3eb12c0e7f356821f90a1d67fe16cd5ef70` passed Ubuntu Python 3.10/3.11/3.13 and Windows Python 3.14, 124 tests per job (Ubuntu skipped 3 Windows-only cases each; Windows 0 skipped). This is **not** test evidence for new STOP/RTM documentation or an OS security certification; check latest CI separately.
- Test reference `test_file.py::test_method` means method in `.source/tests/`; `NOT_MAPPED` is explicit absence. No automatic tool converts trace status into `PASS`. Unknown approvals, missing tests and manually verified claims remain open.

## D. Maintenance and gate rules

1. Requirements must have a stable ID and **testable AC**; record source/owner/version and explicit approval status in the authoritative spec. A feature added or removed must update the primary RTM row and the feature register atomically in the same reviewed change.
2. Implementation planning must reference plan/design/task IDs where actual records exist. `PLAN-xx` in this **system-level** RTM is a scope reference, not a fabricated individual design ID. For detailed feature changes, create [traceability-template.md](../.source/references/traceability-template.md)-style task/design mappings with actual identifiers.
3. Link code to observed repository-relative paths and tests to **existing actual functions**. If no test exists, use `NOT_MAPPED`; do not invent a method to make coverage appear complete.
4. A real verification result needs `command + exact source SHA + environment + actual PASS/FAIL/BLOCKED/SKIPPED/NOT RUN evidence`. Compare current source/spec and invalidate stale evidence before returning to VERIFY/HANDOFF.
5. A **STOP** creates a resumable handoff without changing acceptance statuses. On RESUME, recheck root, source, policy, session and test evidence; any drift sends affected rows back to review.
6. Release evaluation is BLOCKED while required critical/major ACs lack trusted evidence or independent approval. A green CI run alone is insufficient for Windows hostile-race/security/legacy-migration acceptance.
